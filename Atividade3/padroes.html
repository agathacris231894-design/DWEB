Padrões Arquiteturais e Design Patterns

Padrões arquiteturais

São soluções recorrentes para problemas de estrutura e comunicação entre componentes.

API Gateway

Funciona como uma porta de entrada para diferentes serviços.

Pode realizar:

  • Roteamento;
  • Autenticação;
  • Rate limiting;
  • Agregação;
  • Logging;
  • Controle de acesso.

Circuit Breaker

Evita que uma falha em um serviço seja propagada para outros.

Possui três estados:
Closed → Open → Half-Open

Retry

Realiza uma nova tentativa quando uma operação falha.

Deve utilizar estratégias como:

  • Limite de tentativas;
  • Backoff;
  • Jitter.

Bulkhead

Isola recursos para impedir que uma falha consuma todos os recursos do sistema.

Saga

Coordena operações distribuídas.

Exemplo:
Criar pedido → Reservar estoque → Pagar → Confirmar pedido

Se uma etapa falhar, podem ser executadas ações compensatórias.

CQRS

Command Query Responsibility Segregation.

Separa:

  • Commands: modificam dados;
  • Queries: consultam dados.

Event Sourcing

Armazena as alterações como uma sequência de eventos.

Exemplo:
Conta criada → Depósito 500 → Saque 100 → Depósito 200

O estado atual pode ser reconstruído a partir desses eventos.

Design Patterns

São soluções reutilizáveis para problemas recorrentes de design interno.

Exemplos:

  • Factory;
  • Strategy;
  • Observer;
  • Adapter;
  • Repository;
  • Decorator.

Diferença para padrões arquiteturais

  • Arquitetura: estrutura geral do sistema.
  • Design Pattern: solução para problemas internos de design.

SOLID

S — Single Responsibility: Uma classe deve ter uma responsabilidade principal.

O — Open/Closed: Aberto para extensão, fechado para modificação.

L — Liskov Substitution: Subtipos devem poder substituir seus tipos base sem quebrar o comportamento esperado.

I — Interface Segregation: É melhor ter interfaces específicas do que interfaces gigantes.

D — Dependency Inversion: Módulos de alto nível devem depender de abstrações, não diretamente de implementações.
