Principais Estilos Arquiteturais

Monolítica

Toda a aplicação funciona como uma única unidade.

Vantagens:

  • Simplicidade;
  • Menor complexidade operacional;
  • Desenvolvimento inicial mais rápido;
  • Implantação simples.

Desvantagens:

  • Pode apresentar alto acoplamento;
  • Escalabilidade menos granular;
  • Alterações podem exigir novo deploy da aplicação inteira;
  • Pode ficar difícil de manter.

Modular Monolith

Continua sendo uma única aplicação, mas organizada em módulos bem definidos. Busca combinar a simplicidade do monólito com a organização modular.

Arquitetura em Camadas

Divide o sistema em níveis de responsabilidade.

Exemplo:
Apresentação → Aplicação → Domínio → Infraestrutura

Ou:
Controller → Service → Repository → Banco de Dados

Cada camada possui uma responsabilidade específica.

MVC

Significa:

  • Model: dados/domínio;
  • View: apresentação;
  • Controller: recebe requisições e coordena operações.

Fluxo simplificado:
Usuário → Controller → Model → Banco

Arquitetura Hexagonal

Também chamada de Ports and Adapters. Busca manter o núcleo da aplicação independente das tecnologias externas.

Exemplo:
API → Porta → Domínio
Banco → Adaptador → Porta → Domínio

Clean Architecture

Busca manter as regras de negócio independentes de frameworks, bancos de dados e outras tecnologias externas.

Estrutura simplificada:
Frameworks → Adapters → Casos de uso → Entidades

DDD

Domain-Driven Design coloca o domínio do negócio no centro da modelagem.

Conceitos importantes:

  • Entity;
  • Value Object;
  • Aggregate;
  • Repository;
  • Domain Service;
  • Bounded Context;
  • Ubiquitous Language.

É especialmente útil para sistemas com regras de negócio complexas.

Microsserviços

Divide a aplicação em serviços independentes ou relativamente independentes.

Exemplo:
API Gateway
→ Usuários
→ Pedidos
→ Pagamentos
→ Estoque

Vantagens:

  • Escalabilidade independente;
  • Deploy independente;
  • Equipes podem trabalhar de forma independente;
  • Isolamento de funcionalidades.

Desvantagens:

  • Maior complexidade;
  • Comunicação pela rede;
  • Problemas distribuídos;
  • Maior necessidade de observabilidade;
  • Custos de infraestrutura.

Importante: microsserviços não devem ser utilizados apenas porque são uma tendência.

Event-Driven

Utiliza eventos para comunicação entre componentes.

Exemplo:
Pedido criado → Event Bus → Estoque
Pedido criado → Event Bus → Pagamento
Pedido criado → Event Bus → E-mail

Favorece:

  • Desacoplamento;
  • Comunicação assíncrona;
  • Sistemas distribuídos.

Serverless

O desenvolvedor utiliza serviços gerenciados pelo provedor de cloud sem precisar administrar toda a infraestrutura.

Exemplo:
Usuário → API Gateway → Function → Banco

As funções podem ser executadas sob demanda.

Cloud Native

É uma abordagem para construir sistemas aproveitando características da computação em nuvem.

Pode envolver:

  • Containers;
  • Kubernetes;
  • Microsserviços;
  • DevOps;
  • Automação;
  • Observabilidade;
  • Escalabilidade.

Cloud Native não significa simplesmente colocar um sistema em um servidor na nuvem.
